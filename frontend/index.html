How it works

Nabu reviews a new epic against the project's own history, before work starts.
1

Read the tracker history

Nabu pulls the project's tickets, epics, estimates and links from the tracker. Jira and GitHub Issues are mapped into one common format, and every record is tagged with the team or project it belongs to.

2

Learn from finished work

The Historian looks only at work that has already finished. It works out which kinds of tickets overran their estimates, what work tended to block other work, and what epics often forgot to plan.

3

Review each new epic

A day after an epic is created, the Planner reads its tickets and hands them to three specialists:

  • Overrun risk The Estimator flags tickets in areas that have run over before.
  • Blocker risk The Dependency hunter flags work that blocked similar epics but isn't in this plan.
  • Missing work The Gap finder flags work, such as deployment, that similar epics had to add later.

Every warning has to cite the past tickets it's based on.

4

Check the evidence

The Data quality agent rates how much to trust the history behind each warning. The Critic drops warnings with weak evidence, or evidence from a team the viewer isn't allowed to see. The Writer turns what's left into a short summary and a delivery forecast, and each risk gets a suggested fix.

5

Learn from the outcome

When the epic finishes, the Scorekeeper checks each warning against what actually happened. Patterns that came true get more weight next time, and patterns that didn't get less. That's the track record shown on the dashboard.

About this demo

The data is the public issue tracker of Spring XD, an open-source project, from the TAWOS research dataset. The dashboard shows the project as it stood on the date shown there. It uses only what was known by then, with no information from later.
